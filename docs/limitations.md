# Known limitations

Limits of Holocron that are known and either measured or visible in the code. Each says where it comes from.

1. **Cameras serve exactly two concurrent RTSP sessions.** Measured on all six cameras here (TP-Link Tapo) and consistent with TP-Link's documentation, so it is firmware policy rather than a bug; documented-only, it cannot be checked from this repository. This is why the relay (MediaMTX) exists: it holds one session per camera, and the recorder and the live view read from it instead of the camera.
2. **MediaMTX path names must be lowercase alphanumeric.** MediaMTX reads a path's source from an environment variable whose key is cut at the first underscore, so the relay path of a camera is its safe name lowercased with every character outside `[a-z0-9]` removed (`internal/relay/names.go`). Two camera names that differ only in punctuation or case would map to the same path.
3. **The camera password reaches MediaMTX in a child's environment block.** The source URL `rtsp://user:password@ip/stream` is built for the relay and goes into the MediaMTX child's environment and nowhere else (`internal/relay/env.go`); MediaMTX has no out-of-band credential source.
4. **Segment boundaries overshoot the clock mark by up to one GOP.** The recorder copies the streams without re-encoding (`-c copy`, `internal/ffmpeg/args.go`), and a stream copy can only cut on a keyframe.
5. **Tapo cameras keep a separate account for RTSP**, distinct from the TP-Link cloud login; changing the cloud password does not change it. To change the credential Holocron uses, `holocron secret set camera.user` and `holocron secret set camera.password`. (Camera behaviour; documented-only.)
6. **The footage player cannot seek ahead of what has arrived.** A clip is remuxed on demand and streamed, so the response carries `Accept-Ranges: none` and no length (`internal/web/footage.go`), and the browser can only seek inside what it has received.
7. **`status.json` reports the configured relay paths, not the ready ones.** The relay's `Paths` field lists the path names Holocron configured (`internal/status/types.go`); do not read its count as the number of cameras the relay is actually pulling.
8. **Firefox does not connect to a live view that offers only loopback addresses.** It was measured in the live-view stress test (ICE failed against the loopback sandbox, [tests/stress/live-view/README.md](../tests/stress/live-view/README.md)), and the Live page says so when the server offers only loopback addresses (`internal/web/static/live.js`). Watching from Firefox needs a LAN media address (`LiveAdvertiseHosts`, see [ui.md](ui.md)).
9. **Retention is what fits on the disk.** The pruner deletes the oldest segments to keep `ReserveGB` free (`internal/config/KEYS.md`); how many days that is depends on the disk and the cameras' bitrate. `holocron archive stats` shows the rate, the free space and the projected days.
10. **Day folders are invisible to the old PowerShell system.** Holocron files closed segments into `<Camera>\YYYY-MM-DD\` (decision D20, `MoveToDayFolders`); the PowerShell system, which lives in the original repository `windows-terminal-IPCCTV-dashboard`, lists only the files directly in a camera folder. Going back to it therefore starts with `holocron archive flatten --now` ([rollback.md](rollback.md#r2a-put-the-archive-back-flat)).
11. **Windows first.** Windows is the Operator's live system. The Operator reports Holocron also running on a Raspberry Pi 4 (2 GB) and a macOS verification pass; neither is proven by CI, which builds `linux/arm64` and `darwin/amd64` but runs its tests on amd64 Linux, Windows and Apple silicon macOS ([ci.md](ci.md)). The systemd user unit was exercised in WSL2, and the real Windows service install is not individually evidenced (`internal/autostart/service.go`); the Operator did not say which autostart the Pi uses or which parts the macOS pass covered.
12. **`holocron cam discover` sees only this host's own network segment.** It scans private IPv4 networks of this host (or `--subnet`) and learns MACs from the neighbour table, which knows only devices on the same link: cameras on another subnet or VLAN behind a router answer the scan but show the router's MAC (or none), so they can be added but not followed by MAC. Wi-Fi client isolation hides cameras from a computer on the same Wi-Fi. A camera that does not answer RTSP `OPTIONS` without a login, or not on port 554 or a port already in `cameras.json`, is not found. WSL2 in its default NAT mode sees only its virtual network, not the LAN. It does not use ONVIF or WS-Discovery. Verified by the Operator on a real camera network (operator-reported, 2026-11-05); the tests here use local fake RTSP servers and sample neighbour tables (`cmd/holocron/discover_test.go`, `internal/lan/lan_test.go`); the macOS and Windows neighbour-table and routing-table formats (`netstat`, `route`) come from their documentation and samples, not from a capture on those machines. The automatic network choice relies on interface names (virtual ones are dropped); an unusually named virtual adapter can still be kept: `--subnet` overrides.
13. **iPhone and iPad are untested.** Holocron's web app, its certificate steps and live video have not been run on any iOS or iPadOS device, in any browser. Whether iOS accepts the remote CA (a name-constrained CA) and its 199-day certificate is unverified ([docs/ui.md](ui.md#tested-clients)).
