# Troubleshooting

Run `holocron doctor --quiet` first. It checks setup, recording, connections, live view, the web app, the disk and the processes, and prints a `fix:` under every problem ([health check](holocron-cheatsheet.md)). `holocron status` shows what is running; `holocron logs --since 10m` shows what happened (components `host`, `supervisor`, `relay`, `live`, `prune`, `web`, `alerts` and one `ffmpeg:<camera>` per camera). The first table below covers the usual stops; [Holocron: archive layout](#holocron-archive-layout) covers the spool and day folders.

## Something is wrong

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| **Nothing is recording and nothing is coming back.** | The window running an attached `holocron up` was closed (the default Windows logon task runs exactly that). Closing it stops the supervisor, MediaMTX and every `ffmpeg`, and **nothing restarts them**. You get one alert, event id 103, and `status.json` records `StopKind` `window-closed`. | `holocron up --detach` (no window to close), or `holocron up` again. |
| **`holocron status` says NOT RUNNING, or the doctor says the heartbeat is stale.** | `status.json` is older than max(3 x `StatusIntervalSeconds`, 15 s), or the recorded supervisor pid is gone: the supervisor is not running or is stuck. | `holocron logs --component supervisor --since 10m` for why it stopped, then `holocron restart --detach` (doctor's own fix line). |
| **The supervisor crashed and came back by itself.** | Not a fault. The host restarts it after 5 s, alerting as it goes (id 100) and again once it is recording (id 101), up to 5 times in 30 minutes. | Nothing. Out of budget it alerts once more (id 102) and stays down rather than looping all night; then `holocron up --detach` after reading the log. See [When something stops unexpectedly](#when-something-stops-unexpectedly). |
| **`holocron up` says the supervisor refused to start, exit 20.** | Another supervisor holds the archive: a second Holocron on the same root, or the old PowerShell system's recorder, which may still be on the machine. | `holocron doctor --group system` lists the supervisor, host and stray processes. Stop that one (`holocron down` for a Holocron; for the old system, its own stop in its own folder), then `holocron up --detach`. |
| **The supervisor refused to start, exit 21 (alert 102).** | A configuration fault: an invalid `holocron.config.json` or `cameras.json`, ffmpeg missing or older than 5.0, or `RelayExternal` with `RestreamerEnabled` true. Restarting cannot help, so the host does not. | `holocron config validate`, then `holocron doctor --group setup`; fix the file, then `holocron up --detach`. |
| **One camera has gone quiet.** | It has made no file progress for max(`CameraDownAlertMinutes`, one segment + one status tick + 30 s) - see [Alerts](alerts.md) - so it alerted under id 110 and has a `DownSince` in `status.json`. It is judged on file progress alone: a camera that cannot be reached has its `ffmpeg` restarted every backoff period, so the process being alive says nothing. | Check the camera and the network: `holocron cam test "<camera>"` (TCP connect and RTSP OPTIONS, no login) and `holocron logs --component "ffmpeg:<camera>" --since 10m` (doctor's fix line). The supervisor keeps retrying on its own. |
| **The web app will not open.** | The web role is not running (the host restarts it after 5 s and alerts with id 104 after 5 crashes in 30 minutes), or `web.listen` is wrong or taken by another program. | `holocron doctor --group web,setup` (fix lines: `holocron logs --component web --since 10m ; holocron restart --detach`), and `holocron open --print` prints the address (default `http://127.0.0.1:8787/`). |
| **`holocron down` says DID NOT STOP, or the doctor reports an orphan or a stray.** | A child outlived its supervisor, or a process from another program matches the ffmpeg or MediaMTX executable. `down` stops only what it can prove is Holocron's (by pid, start time and image), never by name. | Run `holocron down` again, then `holocron doctor --group system`; for a stray it names the program to stop. |
| **Everything records on direct inputs and the relay never engages.** | The cameras allow only a few simultaneous RTSP sessions (the code assumes two; the number is a property of the cameras and UNVERIFIED in code - see [limitations](limitations.md)). If other clients already hold them, MediaMTX has no free session to pull with. Another NVR, a phone app or the old system's viewer can be the holder. | `holocron doctor --group connections` and `holocron logs --component relay --since 10m`. Close the other clients: the supervisor moves a direct recorder to the relay by itself as soon as the relay serves its camera. |
| **Streams will not connect.** | Wrong address, wrong stream name, or the wrong login. The camera URL is always `rtsp://user:pass@<IP>/<Quality>`, built in one place from `cameras.json` and the stored login. | Check the addresses and `Quality` with `holocron cam list`, test with `holocron cam test "<camera>"`, and re-enter the login if needed (next row). |
| **MediaMTX exits immediately with `ReadDirectoryChanges: Incorrect function`.** | `RestreamerConfigPath` is on the WSL file share, which does not implement it (documented-only: the header of the generated `mediamtx.yml`, measured on MediaMTX v1.21.2). | Set `RestreamerConfigPath` to a local path such as `C:\mediamtx\mediamtx.yml` by editing `holocron.config.json` (the key is not on the `holocron config set` allow-list), then `holocron restart --detach`. |
| **Autostart did nothing at logon.** | The entry is missing, disabled, points at a moved or deleted `holocron.exe`, or was installed with another configuration file. The default task needs an interactive logon. | `holocron autostart status` and the doctor's `system` group name which; its fix lines are `holocron autostart enable` or `holocron --config <your file> install` run from the executable you want started. On Windows you can also check `schtasks /query /tn Holocron /fo list`. |
| **The camera password needs changing.** | - | `holocron secret set camera.password` (reads standard input; also `camera.user`), then `holocron restart --detach` so every camera uses the new login. Tapo cameras keep a separate RTSP account from the TP-Link cloud login; changing the cloud password does nothing here (documented-only: a property of the cameras). |

## Holocron: archive layout

Holocron keeps `<root>\<Camera>\` for the segment being written and the newest closed one, and files the rest into `<root>\<Camera>\YYYY-MM-DD\` ([how it works](how-it-works.md#the-mover)). Three things go wrong there; `holocron doctor` (group `storage`) names each, with the `fix:` line quoted below.

| Symptom | Cause | What to do |
| --- | --- | --- |
| `warn spool backlog`: `the mover is not keeping up ...: more than 4 segments in the spool of <camera> N` (`storage.backlog`) | The mover is not filing. The archive is still read and pruned, but the camera folder grows again. Reasons are in the log: the supervisor is not running, the mover is refused (no valid ownership marker), a conflict (`not filed <path>: the destination ... already exists; neither file was touched`), or a file another program holds open (busy, retried each cycle, debug level). With `MoveToDayFolders` false the check is `info`, not a warning. | `fix: holocron logs --component prune --since 1h (action archive.file names the reason) ; holocron status (is the supervisor running?)`. For a conflict compare the two files and keep one; `holocron archive migrate --now` files what is left and reports it. |
| `warn unseen files`: `N file(s) the pruner cannot see, so it never deletes them and they fill the disk` (`storage.unseen`); or a camera line in `storage.cameras` saying `N segment(s) are MISFILED` | A segment is in a day folder that is not the date in its name, there is something else in a day folder (a foreign file, another camera's segment), or a segment-like name sits deeper than a day folder or in a folder that is not a day. None of them is footage, so none is deleted or counted. | `fix: holocron archive stats ; move each segment into E:\cameras\<camera> or its YYYY-MM-DD day folder, and move anything else out of the camera folders` (your root in place of `E:\cameras`). For `storage.cameras` the fix is `holocron archive stats ; move each to the YYYY-MM-DD folder of its name in E:\cameras\<camera>`. Move by hand only these strays; never write into a day folder otherwise. |
| `holocron archive migrate --now` lists files as `in use by another program` (busy), `changed or gone`, or ends `INCOMPLETE, see above` | Windows: another process holds the file open, so the rename was refused (a sharing violation). Nothing was lost; the file stays in the camera folder. | Close whatever holds it and run `holocron archive migrate --now` again (or wait: the mover retries every cycle). A `CONFLICT` or `ERROR` (exit 1) names the files: compare, keep one, run again. |
| `holocron archive flatten` says `REFUSED: the recorder is running: stop it before putting the day folders back into the spool (...)` | Holocron (supervisor, control endpoint or host process) still runs, and its mover would race the files coming back. | `fix: holocron down`, then `holocron archive flatten --now`. |

The old PowerShell system sees none of this: it lists only the files directly in a camera folder, so it never shows or prunes a filed day. Before it runs again, `holocron archive flatten --now` ([rollback R2a](rollback.md#r2a-put-the-archive-back-flat)). Windows Explorer shows the day folders as ordinary folders inside each camera folder.

## When something stops unexpectedly

Two process scopes answer two different questions, and neither is a polling loop:

| Scope | Holds | Fires when |
| --- | --- | --- |
| `host` | the supervisor and the web app | the **host** process dies, however abruptly |
| `supervisor` | MediaMTX (relay and live) and every `ffmpeg` | the **supervisor** dies, however abruptly |

On Windows a scope is a job object with kill-on-close: it terminates every process in it when the last handle closes, and process exit closes a handle whatever killed the process. On Linux each child leads its own process group and is started with a parent-death signal. So a supervisor that crashes takes MediaMTX and every `ffmpeg` with it: measured on Windows, supervisor and both test `ffmpeg` gone 16 ms after a hard kill and restarted 6.1 s after it (internal/host/README.md). On macOS there is no parent-death signal, so a hard kill of the supervisor leaves its children until the next start reaps them by the registry (CONFIRMED: internal/osx/scope_other_unix.go).

The host process is not the supervisor. It runs the supervisor as a child and restarts it when it stops without being asked to. That split exists because from outside, closing the window and a crash look identical - supervisor gone, `status.json` still saying `running` - and guessing wrong either way is bad. With the split they are different events: closing the window (attached mode) makes the host write `stop.request`, wait for the supervisor and record `window-closed`, while a crash leaves the host untouched and the child exiting is the signal.

Expected or not is read from what the supervisor recorded, never from an exit code alone, because a killed process has no say in its exit code. The stop-request file, a `StopKind` of `requested`, `interrupted` or `window-closed` (trusted only when the document was written by that very supervisor pid), exit 20 and exit 21 all mean do not restart. Anything else is unexpected: the host waits up to 20 s for the instance lock, records `StopKind` `unexpected` with a `LastUnexpectedStop` if the supervisor could not, raises 100, waits 5 s and respawns, and raises 101 when the new supervisor reports `running`. The budget is five restarts in thirty minutes; out of budget it raises 102 and stays down rather than looping all night (CONFIRMED: internal/host/host.go `classify`, `Run`; internal/host/README.md).

**Closing the NVR window is the one stop that nothing recovers from.** It raises its own alert - event id 103, and a Warning rather than an Error, because nothing malfunctioned: somebody closed the window, and the supervisor, MediaMTX, every `ffmpeg` and the web app went with it, which is exactly what that window is for. **Nothing restarts them.** The logon task has no restart policy of its own (restarting is the host's job, and the host has just ended), so the next automatic start is the next logon. Start it again with `holocron up --detach`. `status.json` records `StopKind` `window-closed` and a `LastWindowClose` timestamp, so the web app and the log agree about what happened. An orderly `holocron down` raises no alert.
