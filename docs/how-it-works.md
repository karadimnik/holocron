# How it works

`holocron up` starts a **host**, which runs the **supervisor** as a child, plus the web app. The supervisor owns everything that touches footage: one `ffmpeg` per recording camera, the MediaMTX relay, the optional live-view MediaMTX, the pruner and the mover. Each fact below names the code it was checked against.

## Credentials

No hardcoded passwords. The camera login is stored once with `holocron secret set camera.user` and `holocron secret set camera.password` (each reads the value from standard input) in the credential store chosen by `secrets.backend` - on Windows the Credential Manager when it answers, else an encrypted file; on Linux and macOS the encrypted file; or the environment ([configuration.md](configuration.md#logging-alerts-secrets-and-the-web-app)). `holocron secret import --from camera_creds.xml` moves a login saved by the old PowerShell system into the store (CONFIRMED: internal/secrets/open.go, cmd/holocron/secretcmd.go).

Where the password goes (CONFIRMED: internal/ffmpeg/args.go, internal/ffmpeg/inputlist.go, internal/relay/README.md, internal/supervise/loop.go `cameraSpec`):

* It is never written to a log: every line of every child's output passes a redactor that masks `scheme://user:pass@` and every registered secret before it reaches a file.
* It is never written to the generated relay config. Each relay path keeps `source: publisher` and the real camera URL reaches MediaMTX in the child's environment block at launch (`MTX_PATHS_<NAME>_SOURCE`).
* On the relay path it reaches no command line at all, because recorders read `rtsp://127.0.0.1:8554/<path>`; `ffmpeg` refuses to build a command line that carries a credential unless told to.
* A recorder that has to take a direct camera input still keeps the password off its command line: the URL, transport and timeout go into a small `ffconcat` list file in `_state\inputs\`, created owner-only before the URL is written and deleted after the child exits (`ffmpeg -f concat -i <list>`).

The rest is the floor rather than an oversight: while a direct child runs, the password is in the list file and in Holocron's memory, and `ffmpeg` prints the credentialed URL in its own error text, which is why its output is redacted before it is stored. See [limitations](limitations.md).

## Recording

Recording is opt-in per camera (`holocron cam enable`). The supervisor keeps exactly one `ffmpeg` child per camera whose `Record` flag is true and reconciles against `cameras.json` every `ReconcileSeconds`, so enabling, disabling or changing a camera's address takes effect without a restart. A child that exits is restarted with backoff (3, 6, 12, 24, 48, then 60 s; reset after a child stayed up `HealthyResetSeconds`), and one whose newest file stops progressing for `StallFactor` x `SegmentSeconds` is killed and restarted by the watchdog. Only one supervisor can run per archive: a second one exits with code 20 and names the holder (CONFIRMED: internal/supervise/plan.go, stall.go, manager.go, README.md; internal/osx lock).

Streams are copied, never re-encoded (`-c copy`), so recording costs almost no CPU and the footage is exactly what the camera sent. Segments are 15 minutes (`SegmentSeconds`) and aligned to the clock (`-segment_atclocktime 1`) give or take: a stream copy can only cut on a keyframe, so each boundary overshoots the mark by up to one GOP (documented-only: ffmpeg behaviour; the arguments are CONFIRMED in internal/ffmpeg/args.go).

Footage lands in one folder per camera. ffmpeg cannot create folders, so it always writes flat into the camera folder (the spool); the mover (below) files each closed segment into a day folder named for the local date written in its name (decision D20):

```
E:\cameras\
  Front_Entrance\Front_Entrance_20261027_101501+0200.mkv   the spool: the segment being written
  Front_Entrance\Front_Entrance_20261027_100001+0200.mkv   and the newest closed one
  Front_Entrance\2026-10-26\Front_Entrance_20261026_233001+0200.mkv   a filed day
  Rear_Balcony\    ...
  _state\status.json        what `holocron status`, the doctor and the web app read
  _state\                   also: supervisor.lock, stop.request, host.json, archive-owner.json, inputs\
  _logs\holocron.log        the program log (host, supervisor, pruner, web, alerts), rotated at LogMaxBytes
  _logs\audit.log           every logged action, rotated at four times LogMaxBytes
  _logs\restreamer.log      MediaMTX output, redacted
  _logs\liveview.log        the live-view MediaMTX output, only when live view is on
  _logs\<Camera>.log        per-camera ffmpeg output, relayed by the supervisor, redacted, rotated the same way
```

(CONFIRMED: internal/app/paths.go, internal/app/logging.go, internal/supervise/supervisor.go, loop.go.) `holocron logs` reads, filters and follows `holocron.log`. A rotating log never blocks recording: a reader holding the file open only delays the rotation (logged once), and lines that cannot be written are counted in one "log write failed ... dropped" notice afterwards (CONFIRMED by tests: internal/logx/rotate_test.go).

The day folder is the local date in the file name, so the repeated hour of the clock change stays in one folder with both offsets. Every Holocron reader goes through one library, `archive.Layout`: the Footage tab, `holocron archive stats`, `archive compare`, the doctor and the disk figures read the spool and every day folder; the status tick, alert 110 and the stall watchdog read only the camera folder while it holds the open and the last closed segment, one listing per camera however many days are filed. The pruner deletes a filed segment in the same oldest-first order, under the same gates, as one in the camera folder, and nothing in a day folder that is not footage is ever deleted. A day folder it empties, or finds empty, is removed once its date is past (earlier than today's local date). A file under a day folder that is not the date in its name is misfiled: it is not footage, and `archive stats` and the doctor report it. A folder named like a day that is not a real date, a link or a junction is never entered (CONFIRMED: internal/archive/README.md, internal/prune/README.md).

The old PowerShell system lists only the files directly in a camera folder, so it neither shows nor prunes a filed segment. Pointing it at a root Holocron has filed means putting the archive back flat first (`holocron down`, then `holocron archive flatten --now`: [rollback R2a](rollback.md#r2a-put-the-archive-back-flat)).

Three details in there are not preferences:

* **MKV, not MP4.** The cameras emit `pcm_alaw` audio, and MP4 refuses `pcm_alaw` with stream copy. MKV is also the only container here that survives a crash: a file that was being written when the power went out still plays. The `fmp4` profile exists and re-encodes the audio to AAC (documented-only: measured on the Operator's cameras; the profiles are CONFIRMED in internal/config/config.go).
* **The `+0300` suffix.** Segment names are `<Camera>_YYYYMMDD_HHMMSS+HHMM.mkv`: local time plus the UTC offset (`%z`). Without the offset in the name the repeated hour at the end of daylight saving would silently overwrite the first one. ffmpeg's `TZ` handling is unreliable on Windows, so Holocron removes `TZ` from the ffmpeg child's environment there (CONFIRMED: internal/ffmpeg/README.md, args.go).
* **Intervals do not follow the wall clock alone.** Timers and deadlines run on a monotonic clock and file ages on the wall clock, and time the supervisor was not ticked (a suspended PC, a clock step) is not counted, so a daylight-saving change cannot stall every timer or make the watchdog kill every healthy child and alert 110 fire for every camera (CONFIRMED: internal/supervise/stall.go `tick`, `blindWall`). Local time is only ever shown: log stamps, segment names, and the timestamps in `status.json`, which carry their offset (`+03:00`) (CONFIRMED: internal/status/types.go `TimeLayout`).

## Retention

The pruner runs at start and then every `PruneIntervalSeconds`, and watches free space rather than age. When free space falls below `ReserveGB` it deletes oldest-first until `ReserveGB + PruneHysteresisGB` is free, which stops it thrashing at the boundary. It never deletes the segment being written. The layout does not change any of this: the pruner counts the camera folder and every day folder together, so retention is still the free-space watermark and not a number of days. It moves with the bitrate, the camera count and `ReserveGB`. If nothing deletable is left and free space is still below `ReserveGB` it alerts once (id 121) and keeps recording. Set `MaxRetentionDays` if you also want an age cap; a run that would delete more than `MaxAgePruneFraction` (default half) of the archive by age deletes nothing by age and alerts once (id 122), so a mistyped retention cannot empty it. The pruner refuses a root that is unsafe or that the supervisor has not claimed with an ownership marker (`_state\archive-owner.json`), and alerts once (id 120) (CONFIRMED: internal/prune/README.md, state.go).

**Do not plan from a number in a document.** The rate footage accrues at depends on how many cameras are up, which stream each one is on and how much the scenes move, so it drifts with the system rather than sitting still. `holocron status` and `holocron archive stats` print the rate measured over the archive as it stands (GB per day), with the days of headroom left - that figure is the one to plan from, because it is the only one that is current. `holocron prune --dry-run` shows what the pruner would do now.

## The mover

ffmpeg cannot create folders, so it writes every segment flat into the camera folder (the spool). The mover, a loop of the supervisor that runs every `MoveIntervalSeconds` (60), files each closed segment into the day folder of the date in its name: `Front_Entrance\Front_Entrance_20261026_101500+0200.mkv` becomes `Front_Entrance\2026-10-26\Front_Entrance_20261026_101500+0200.mkv`. The camera folder keeps only the segment being written, the newest closed one and one younger than the margin. The mover runs only when the supervisor found or wrote a valid ownership marker for the root at start; otherwise it logs a warning and files nothing (CONFIRMED: internal/supervise/supervisor.go:202, 586-589).

What it moves: a plain file (never a link, junction or folder) named as a segment of that camera, that is not one of the two newest segments of the camera folder, and whose last write is at least `MoveMarginSeconds` (120) old. A zero-byte segment is filed like any other. Oldest first, at most `MoveMaxPerCycle` (200) per camera per cycle, so a first run over a large flat archive spreads its disk work over a few minutes. A day folder is created inside the camera folder, never anywhere else. Each file is checked again just before it moves (still a plain file, same size and write time, its folders not links), and the move is a rename on the same disk, which never replaces a file: if the day folder already holds that name, both files stay as they are and the log says so on every cycle until someone resolves it (CONFIRMED: internal/archive/move.go).

Failure is harmless: a segment that does not move stays in the camera folder, where the Footage tab, the status and the pruner see it exactly as before. On Windows a file another program holds open is retried on the next cycle; a cycle that only met such files or errors waits twice as long, up to ten intervals. A rename either happened or did not, so a crash or power cut mid-cycle leaves nothing to repair; on macOS, and on a Linux filesystem without an atomic no-replace rename, a move is a hard link then the removal of the old name, and one interrupted between the two leaves the file under both names until a later cycle, a minute on, removes the old name and logs it as an interrupted move finished. The mover and the pruner never run at the same moment. The log lines are action `archive.file` (component prune): info when a cycle moved something, warnings for conflicts and errors, debug for busy files (CONFIRMED: internal/supervise/move.go). `holocron doctor` warns (`storage.backlog`) when a camera folder holds more than 4 segments once the supervisor has run for 15 minutes, and (`storage.unseen`) about files the pruner cannot see: a misfiled segment, anything else in a day folder, a segment-like name in a folder it does not enter (CONFIRMED: cmd/holocron/doctor_storage.go).

`MoveToDayFolders` false switches the mover off at the next reconcile, without a restart; day folders already filled stay and are still shown and pruned.

**Migrating existing history.** The first start over a flat archive makes the mover file it (at the defaults 200 per camera per minute, oldest first). `holocron archive migrate` does the same at once and reports it: without `--now` it is a dry run that moves nothing and prints, per camera, what would be filed and how many segments stay; `--now` applies it in cycles of `MoveMaxPerCycle` until nothing eligible is left. It uses the mover's rules (the two newest segments of a camera and any written less than `--margin` seconds ago stay; the margin defaults to `MoveMarginSeconds` and is at least 30), is safe while the recorder runs (both movers rename without replacing, exactly one of them reports each move, and a file the other moved first is skipped, not an error), and can be stopped at any time and run again. It exits 1 when refused, or when a conflict (the destination name exists: both files stay) or an error remains; a file another program holds open is listed as busy and the next run tries again. `--camera NAME` limits a run to one camera (CONFIRMED: cmd/holocron/layoutcmd.go, commands help).

**Going back to flat.** `holocron archive flatten` puts every filed segment back into its camera folder and removes each day folder this empties. It is a dry run unless `--now`, refuses while Holocron runs (`holocron down` first), never replaces a name (a conflict leaves both files) and leaves files in a day folder that are not footage of that camera, saying so. Afterwards `holocron up` files the segments again unless `MoveToDayFolders` is false. It is step R2a of the [rollback](rollback.md#r2a-put-the-archive-back-flat).

## Transport: the relay

These cameras allow very few simultaneous RTSP sessions (the code treats it as two; the number is a property of the cameras and UNVERIFIED in code), which is the whole reason MediaMTX is here. With the relay running, each camera is pulled exactly once and MediaMTX serves every consumer from that one session: the recorders, and the live-view instance's `main` paths. The supervisor starts MediaMTX as its own child, so there is one thing to autostart rather than two. A relay that exits is restarted with the same backoff as a camera.

The choice is made per start attempt, per recorder: if the relay is serving that camera it is used, and if it is not, a direct camera connection is used instead. At a cold start the recorders are held while the relay comes up, at most `RelayReadyWaitSeconds` per camera, so they do not start direct by default. A relay that dies is left behind at the next restart of the recorder and one that comes back is picked up without relaunching anything (CONFIRMED: internal/supervise/plan.go). `holocron status` shows which input each recorder is actually on (`relay` or `direct`), and the doctor warns about a camera recording direct.

A recorder that had to take a direct connection gives the camera slot back on its own once the relay is serving that camera again: the supervisor kills that one child (not counted as a failure) and starts it on the relay (CONFIRMED: plan.go, `ReasonMoveToRelay`). A recorder on the relay needs no watch: if the relay dies, `ffmpeg` loses its input, exits, and the next start decides again by itself.

The generated `mediamtx.yml` contains no password. Every path is left as `source: publisher` in the file and the supervisor supplies the real camera URL on the child's environment block at launch.

The relay's control API, which the supervisor asks whether a path is serving, needs a login. Holocron generates one (user `camrelayapi`), a random 32-byte secret kept as 64 hex characters in an owner-only file `relay_api_secret.txt` in the auth folder, and `mediamtx.yml` holds only its SHA-256; every caller sends it in-process, never on a command line. Reading and publishing RTSP on loopback still needs no login. The file is created at the first start when it is missing, and the supervisor checks every status interval that the config still carries the stored login: if it does not, the file is rewritten and the relay restarted (not counted as a failure) (CONFIRMED: internal/relay/login.go, internal/supervise/mtx.go `rewriteIfStale`).

**A refused login is not a dead relay.** If the API answers 401 or 403 the relay is still running and serving, so every consumer is kept on the relay - a refused login could otherwise send every recorder to a direct camera input and take the camera's second session. What is lost is only the view of which paths are serving: a camera whose path has no stream is retried on the relay at each restart instead of falling back to direct, until the login is fixed. The supervisor raises alert 130 once per episode and logs when the login is accepted again; `holocron doctor` (group `connections`) reports the refusal. `holocron restart` fixes it, because the relay start rewrites the config to the stored login (CONFIRMED: internal/relay/api.go, internal/supervise/loop.go, cmd/holocron/doctor_connections.go).

## Status and the web app

The supervisor rewrites one file, `_state\status.json`, every `StatusIntervalSeconds`; it is the heartbeat. `holocron status`, `holocron doctor`, the host and the web app read it and nothing else of the supervisor's, so none of them can cost a camera session. A supervisor counts as running when the heartbeat is no older than max(3 x `StatusIntervalSeconds`, 15 s) and the recorded pid is alive with the recorded start time (CONFIRMED: internal/status/verdict.go). The document holds the supervisor state and uptime, the relay, disk figures with the measured rate and days left, the pruner state, per camera the record flag, child alive, relay or direct input, the newest segment, restarts in the last hour and the last error, and the most recent log lines (`StatusEventCount`) (internal/status/types.go).

The web app (`holocron up` starts it beside the supervisor; `holocron web` runs it alone) shows that state as Dashboard, Settings, Footage and Live screens ([ui.md](ui.md)). A crash of the web app never touches recording: the host restarts only the web child, after 5 s, then 10, 20, 40 and 60 s, and raises alert 104 when it crashes 5 times in 30 minutes (CONFIRMED: internal/host/README.md).

## Autostart

`holocron install` creates exactly one entry that starts Holocron for this OS and records what it created; `holocron uninstall` removes exactly that (CONFIRMED: cmd/holocron/commands.go help). On Windows the default is a Scheduled Task named `Holocron` that runs at logon as you, with an interactive, limited token (no elevation, no prompt); `--mode service` installs a Windows service instead (administrator rights), Linux gets a systemd user unit and macOS a launchd agent. The task has no execution time limit, ignores a second instance, and has no restart policy of its own: restarting a crashed supervisor is the host's job. `holocron install` is idempotent: running it again does not add a second entry (CONFIRMED by the command help; the task settings by: internal/autostart/autostart.go, logon.go). Details, the `--window visible|hidden` choice and the checks are in [autostart.md](autostart.md).

**The default task opens a console window running `holocron up`, and closing that window is a stop.** `--window visible` (the default) runs the attached `holocron up` in a console window on the desktop; closing it stops the supervisor, MediaMTX and every `ffmpeg` and raises alert 103, and **nothing restarts them** until the next logon or the next `holocron up`. `--window hidden` runs `holocron up --detach` with no window at all (CONFIRMED: internal/autostart/autostart.go `WindowVisible`, `WindowHidden`; internal/host/host.go `windowClosed`).

`holocron install` never touches the old PowerShell system's Scheduled Tasks; `holocron autostart status` lists them read-only, and `--i-know-old-tasks-are-enabled` acknowledges that they are still enabled (CONFIRMED: internal/autostart/autostart.go `OldTasks`). Two supervisors cannot record into one archive: the second exits with code 20.
